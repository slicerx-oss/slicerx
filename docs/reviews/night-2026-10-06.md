## Findings

Each finding lists the area, severity, evidence and the commit that fixes it, or a write-up when the fix is too big or risky for tonight.

### 1. Paths outside the mapped extruder's reach were not blocked (H2D, H2C)

- Area: G-code safety, multi-material.
- Severity: high. The G-code drives a nozzle past the part of the bed it can reach.
- Evidence: `preflight::check_toolpaths` checked the bed, exclusion zones and height, but never `extruder_printable_area` (H2D: left 0 to 325 mm, right 25 to 350 mm). The manual filament map is used without any reach check. The auto map (`nozzles.rs`, `allowed`) checks only the box of each filament's parts. Reproduced with `sx slice --request` on the H2D machine profile: two copies of the `cube.stl` CLI fixture, one at x 14 with `filament_map` [2, 1] (manual), and a one-color plate at x 40 with a 15 mm brim and 3 skirt loops (auto: the filament goes to the right master extruder, and its skirt reaches x 23.4). Both produced G-code before the fix.
- Commit: d9366ad `fix(core): block paths outside the mapped extruder's reach`. Each path's extruder now comes from the filament map, and points outside that extruder's box block the slice (`outside_extruder_reach`), matching Orca's `GCodeProcessor::check_multi_extruder_gcode_valid`. Centered plates and correct maps still pass.

### 2. The auto filament map ignores skirt, brim and supports (brim fixed, rest write-up)

- Area: engine, multi-material (H2D, H2C).
- Severity: medium. Since d9366ad this is blocked, not printed, but the plate in finding 1 fails to slice when the other extruder would print it fine.
- Evidence: `nozzles.rs` `Map::resolve` reads `Usage.boxes`, the box of each filament's parts. Orca also clips each object's brim to its extruder's reach (Brim.cpp, `extruder_unprintable_area` in the brim area generation).
- Brim: fixed in ec227bb `fix(core): cut a brim to the reach of the extruder that prints it`, as Orca's Brim.cpp `outer_inner_brim_area` does (test `safety::a_brim_stays_inside_its_extruders_reach_as_orca_clips_it`).
- Still open: the auto map tests only the parts' boxes, so a skirt or support past a part can still land beyond the chosen extruder's reach. d9366ad blocks such a plate. Proposed: grow each filament's box by its skirt and support extent before the reach test. Not done tonight, because it changes the auto map's choices and needs parity runs against Orca.

### 9. Models with non-ASCII file names failed to load or lost their names (desktop)

- Area: app, Windows (also macOS: the cause is the webview's IPC, not the OS).
- Severity: high for users whose files are not named in plain ASCII.
- Evidence: the desktop app sends the file name in the `x-sx-name` IPC header, for `load_mesh` (where the name's ending picks the format) and for `save_file`. Tauri's IPC builds a `Headers` object, which takes only characters up to U+00FF; Node's `Headers` throws on "Кубик.stl" and "立方体.stl" just as Chromium (WebView2) does. In the shell, `HeaderValue::to_str` takes only visible ASCII, so "Würfel.3mf" fell back to "model.stl" (a 3MF parsed as STL) and the save dialog fell back to "plate.gcode". The Bambu Connect hand-off already percent-encoded its headers.
- Commit: 43a30b0 `fix(desktop): load and save files whose names are not plain ASCII`. The webview percent-encodes the name, and the shell decodes it in a new `header::text`. Tests: `apps/desktop/test/name-headers.test.ts` (fails before the fix with the ByteString error) and `header::tests`.

### 16. Jerk lines far more frequent than Orca's

- Area: engine (G-code), parity.
- Severity: low. Extra `M205` lines, not different motion limits.

### 18. The Windows H.264 still decoder trusts a u32 length (write-up)

- Area: Windows, camera (`packages/connect/stills/src/windows.rs`).
- Severity: low (theoretical).
- Evidence: `decode_with_mf` sizes the Media Foundation buffer with `u32::try_from(len).unwrap_or(u32::MAX)` and then copies `access_unit.len()` bytes into it. An access unit over 4 GB would overrun the buffer. Real camera frames are far smaller, and a test would need a 4 GB slice. A one-line fix: return `Ok(None)` when the length does not fit in u32.

### 19. path_parity: 21 of 105 cases differ from Orca (write-up)

- Area: engine correctness (infill anchors, gap fill, rafts, sparse patterns).
- Severity: low to medium. Extrusion totals agree; the differences are joins and directions.
- Evidence: `path_parity.py` on Windows, sx bench-release against OrcaSlicer 2.4.2. Many are already documented in docs/core-features.md (lightning trees cannot match line for line; the joins of 3D honeycomb and cross zag break more). Two stand out:
  - Grid on the block: 369 strokes against Orca's 92, while docs/core-features.md records 184 against 92 for the same case. Joins break twice as often as the doc says. The public history is squashed, so the change since the doc could not be bisected here.
  - Anchors on the gear (`anchor-default-gear`, `anchor-a10-m20-gear`): 315 strokes against 195, and `raft-1-cube`: the support interface direction histogram is 0.93 apart. The raft cases are fixed in cbfab84: one- and two-layer rafts laid their contact lines at 90 and 45 degrees where Orca lays 135 (`raft_interface_angle`, and the interface id a contacts-only layer takes in `generate_support_layers`). raft-1, raft-2 and raft-3 now pass.
- The anchor cases that fail are all grid infill on the gear, and `anchor-none-gear` has the same 5395 extruding moves as Orca but 315 strokes against 195: the lines are the same, the order is not. In that file SlicerX opens 315 `;TYPE:Sparse infill` sections against Orca's 180 and retracts inside sparse infill 252 times against 116, so the grid's lines are split into more groups (or interleaved with other features) and joined by retracting travels about twice as often. That costs print time and stringing, not material.
- Next: compare how the infill phase chains grid fill collections (docs/core-features.md: ShortestPath.cpp `chain_extrusion_entities`, GCode `extrude_infill`) on one gear layer, and bisect the grid strokes against the doc's 184 in the private history. Not changed tonight.

### 29. Opening a link on Windows could run a command (security)

- Area: Windows, desktop app.
- Severity: severe. Any https link the webview handed to `open_external` could start a program as the user.
- Evidence: `chatgpt::open_in_browser`, `agents::open_deeplink` and the `.mcpb` file open ran `cmd /C start "" <link>`. Released 0.1.1 is affected; whether to advise users or ship a hotfix is for the owner.
- Exploitability (traced in this branch's sources; it reflects 0.1.1, which has the same callers):
  - What reaches the vulnerable commands. `open_external` is called only by the store pages through `routes.ts` `openExternal`: sign-in, dashboard, creator pages and the account page. Each URL is the edition's own origin plus a fixed route, and the creator handle, which comes from Supabase, is passed through `encodeURIComponent`, so an `&` in a handle arrives as `%26`. The Rust side also opens the ChatGPT sign-in URL (`chatgpt.rs`), built from fixed OpenAI endpoints. `open_deeplink` gets only the Cursor install link that `packages/mcp/src/agents.ts` builds from a fixed name and the hub's own config, and it must start with `cursor://`. The `.mcpb` file open uses a path in the app's cache folder.
  - What does not reach them. Every other link in the webview is a plain `<a target="_blank">`: assistant (LLM) citations (`pilot/ui/citations.tsx`), the printer's error help URL (`device-dialog.tsx`), About and legal links, and the slicer download link. Tauri's opener plugin opens those with ShellExecute, never `cmd`, and only within the scope in `capabilities/default.json` (slicerx.app, the Discord server, ollama.com/download and the Bambu Connect wiki page). Store items, 3MF or model metadata, printer-reported URLs and MCP tool results are not passed to `open_external` anywhere.
  - What an attacker would need. Script running in the webview, which could call `invoke('open_external', ...)` with any https URL. The CSP allows only the app's own scripts (`script-src 'self' 'wasm-unsafe-eval'`, no inline script), and nothing in the app renders raw HTML (no `innerHTML`, no `dangerouslySetInnerHTML`). No path was found that lets a third party's URL reach these commands with or without a click.
  - What users did hit. The URLs the app builds contain `&` themselves, so on Windows cmd cut them at the first `&` and tried to run the rest as commands. The ChatGPT sign-in page and the Cursor install link most likely opened without their parameters, a broken flow rather than an attack. A Windows user name containing `&` would also break the `.mcpb` open. fd7aa00 fixes all of these.
  - Assessment: a real defect with no known attacker-controlled path. It fits the planned 0.1.2 rather than needing an emergency hotfix by itself; it would become urgent if any change lets webview content run script or pass outside URLs to `open_external`.

### 30. Console programs started without CREATE_NO_WINDOW (Windows)

- Area: Windows, desktop app.
- Severity: low to medium. Windows semantics, not observed in the app tonight: a console program started by a windowed one opens its own console window, which can take the focus.

### 32. Printer scan on Windows depends on a firewall prompt (write-up)

- Area: Windows, printer connect, first-run.
- Severity: medium for Scan only. Adding by IP connects outbound and does not need it.
- Evidence: discovery listens for announcements (Bambu Lab SSDP and mDNS) on inbound UDP. On Windows, the first listener raises a Windows Firewall prompt for the app; a dismissed or denied prompt leaves Scan finding nothing, with nothing in the app saying why. Neither the installer nor the app adds a rule (no `netsh` or firewall code in apps/desktop).
- Proposed: when a scan finds nothing on Windows, say a blocked firewall prompt is a likely cause and offer "Enter IP instead"; optionally the NSIS installer adds an inbound rule for the app on private networks (an installer change, for the owner to decide).

### 34. The mobile package's tests cannot start on Windows (write-up)
