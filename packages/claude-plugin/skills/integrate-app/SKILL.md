# Build SlicerX into an app

The SlicerX integrator kit has the full instructions. Read them first, then follow their steps in order.

1. Read the agent guide: the resource `slicerx://docs/integrators/agents`. If you cannot read resources, read `node_modules/@slicerx/mcp/AGENTS.md` in the developer's project, or `docs/integrators/AGENTS.md` in a SlicerX clone. Keep `slicerx://docs/integrators/quickstart` open for tool options, result fields and error codes.
2. Get the packages into the project (step 1 of the guide). They are not on npm yet: install the tarballs from the developer's kit folder, or pack them from a clone with `node scripts/pack-integrator-kit.mjs <folder>`.
3. This plugin already connects you to the SlicerX MCP server, so step 2 of the guide is done. Check it: call `slicerx_estimate_file` with `{ "model": "sample:cube-20" }` and expect `time_s` above 0. When the developer uses another coding tool too, give them that tool's setup from the guide's table.
4. Choose the path first. Make your own edition (white-label) is the main path when the product is a slicer: follow "Path A" in the guide (it needs a clone of the SlicerX repository with an `upstream` remote and builds a separate app that their own app launches; copy an edition config, build with `pnpm edition:build editions/<id>/edition.config.ts --target desktop`, sign with their own certificates, update by pulling SlicerX releases). Required credit is a small "Made possible by SlicerX" linked to https://slicerx.app/support, in About and their docs (the edition config shows it and cannot drop it); they cannot use the SlicerX name or logo; the profiles and printer images are AGPL (see NOTICE), they offer the source through `legal.sourceUrl`, and they should get legal advice before shipping commercially. Tell them the guide's list of what a config leaves as SlicerX, and that this is not legal advice. Embedding pieces is Path B and an installed SlicerX is Path C. For Path B, interview the developer (step 3) in one message before you write code: which parts (viewport, slicing, printers and sending, profiles and presets, mimir, the full app), their framework and shell, their brand (accent, surfaces, fonts, light or dark), where models live, and whether they have the `sx` engine. Assume the local path: the app slices local files with no SlicerX account and no token, so do not ask about accounts, the vault, cloud slicing or `.sxlock`. Only if the developer brings up cloud or sharing, use the guide's section "Optional: cloud and locked projects". Read `package.json` first and only confirm what it already says. Write back a short plan per part and wait for a yes.
5. Build with the recipes (step 4), starting with the local ones: the viewport, slicing through the local MCP server or the `sx` engine, and profiles. Slicing runs in a main process or a Node service, never in the browser.
6. Show the pre-alpha agreement before the first SlicerX part, and wire `onError` to the app's crash reporting (step 5).
7. Theme every part with the developer's brand (step 6): `createTheme` from `@slicerx/embed`, `EmbedTheme` around the parts, `scene` colors for the 3D view, and a contrast check with `slicerx_theme_create`. Fix every failing pair.
8. Finish with the guide's checklist: the app builds and type checks, every part is themed, the agreement shows, the server reads only the user's folders, no secret is in the code, and nothing approves printer actions.

Rules that hold whatever the developer asks: never approve a print start, a resume, raw G-code or a printer adjustment through `slicerx_approve`, and never write app code that does; any token (only the optional cloud features use one) goes in the keychain or the environment, never in code; give the server only the folders the user picked.
