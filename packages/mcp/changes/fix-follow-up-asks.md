### Changed

- `slicerx_design_plan` 1.19.0 (from 1.18.0), in the mimir tab, and `slicerx_design_put_plan` 1.11.0 (from 1.10.0) take an amend that moves a planned feature onto another one (its `on`), for a build's amend and for a change the person asked for, in a whole plan sent with `amends`. The stored plan keeps the new `on`, and `slicerx_design_check` holds the part to it: a deck planned on the base plate but built on the piers passes once an amend says it stands on the piers. Before, such an amend was refused with `features: an amend changes sizes only; Deck keeps on: "Base plate"`, so the item could never pass. A feature restated without its `on` keeps the plan's, as other fields left out do. An amend whose only change is an `on` is taken, and its summary names no size ("Plan changed (revision 2). Build to it as changed"). A row of holes' `recess`, the part's shape and, over MCP, the plan fields an amend keeps are still refused as before.

### Fixed

- `slicerx_design_check` 1.26.0 (from 1.25.0) no longer tells a follow-up that its change broke an item that was already failing before it. The plan keeps the items its last check failed, and when the person's change begins (an amend with `asked`, or a later request that changes a part whose fix round was used) it notes which were failing then. A check after the change that fails only on those items lists them as any failed check does, returns them in `failedBefore`, and is not told to fix or undo the change; it does not count toward the undo either. A check that fails on an item that passed before the change is still told that the change broke it, then to undo it. A pass in between clears the list. The project file keeps the items a plan's last check failed with the plan (`failing` in Metadata/slicerx_plans.json), so this holds after the project is opened again. Before, a deck link that failed in the first build was blamed on every follow-up after it, and a second check asked to undo a change that had nothing to do with it.
