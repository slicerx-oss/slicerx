# packages/settings (sx-settings and @slicerx/settings)

Settings schema, Easy mode and profile import. One folder, two languages, one set of data files:

- `schema.json`: 740 keys (every FFF preset key of OrcaSlicer main 97700c5, with its name, type, range, default, enum values and tier, plus the sleipnir keys and a few machine flags of our own) with type, unit, default, range, enum values, group, dependencies (`enabledWhen`), effect text and `invalidates` (first slice stage). Key names follow OrcaSlicer's (commit pinned in `knowledge/settings.yaml`) so profiles interchange. The file is checked in as this package's own data, with the mimir rules and bounds from `knowledge/settings.yaml`. Labels are ours (`scripts/labels.json`); hand-written groups, stage rules, dependencies and effects live in `scripts/schema-extra.json`.
- `easy-map.json`: Easy controls to Orca keys as JSON expressions (`linear`, `round_to`, `floor`, `ceil`, `add`, `mul`, `min`, `max`, `clamp`, `table`, `base`, `ref`, plus `scale` rules for speeds and accelerations). Both languages interpret it.
- `legacy.json`: Orca's `handle_legacy` renames and value maps, its obsolete keys, and the keys Bambu Studio and other forks add that Orca drops. Interop facts for reading users' Orca and Bambu Studio files, checked in as data.
- `knowledge.json`: the small material and printer table `planSettings` reads, compiled from `knowledge/filaments` and `knowledge/printers` by `pnpm gen:knowledge`.
- `profiles/printers.json`: our own printer profiles, one per model in the printer catalog, generated by `node scripts/gen-profiles.mjs` (see the guide). Filament profiles come from `knowledge.json` and process presets from `easy-map.json`; `printer-models.json` maps catalog model ids to knowledge printer ids.
- `fixtures/`: `profiles/` (14 small profiles written for the tests, with `inherits` chains, `nil` lists and a key Orca drops), `easy-cases.json` (42 cases, from `scripts/gen-easy-cases.py`), `validate-cases.json`, `knowledge-catalog.json`. Rust and TypeScript both pass all of them. The Rust import test also writes `packages/contracts/fixtures/settings-config.json`, which a TypeScript test reproduces.

Docs: [tiers and Easy mappings](docs/tiers.md) for building the settings UI, [guide](docs/guide.md) for integrators, and the [settings reference](docs/reference/index.md) with every key (generated from `schema.json` by `pnpm gen:reference`).

## Public API

```ts
SETTINGS, settingDef(key), settingsFor(section), invalidates(key), defaultConfig(section?)
applyEasy(easy, base), goalEasy(goal), matchGoal(easy), easyControlFor(key)
importOrcaProfile(json, resolve): ProfileImport     // .config, .chain, .unknownKeys, .ignoredKeys, .nilKeys, .invalidKeys
exportOrcaProfile(config, { name, section, inherits? }), mergeConfigs(...configs)
validate(config): SettingIssue[]                   // checkValues + checkConflicts, errors first, fixes suggested only
isEnabled(def, config), disabledKeys(config)
diffConfigs(before, after, { easy? }): ConfigDiffEntry[]   // earliest slice stage first, one plain reason per key
toSettingsPlan(from, to, before, after, { sources?, easy? }): SettingsPlan
planSettings(from: SetupRef, to: SetupRef, base?: PrintConfig, opts?: PlanOptions): SettingsPlan   // material, printer or nozzle switch, and goals
applyPlan(config, plan): PrintConfig
listMaterials(), listPrinters(), materialKnowledge(id), printerKnowledge(id)
registerSettingText(text) / clearSettingText()   // overlay wording from a text package
importProject({ projectSettings, modelSettings?, layerRanges? }): ProjectImport   // Bambu Studio and Orca .3mf metadata
readPresetBundle(entries): PresetBundle   // Orca and Bambu Studio preset bundles, unzipped by the caller
importPresetFiles(files, { printerId?, printer? }): Promise<ImportedPreset[]>   // inherits resolved, an import report each
importLayers(layers), buildReport(input), reportText(reports, { keys? })   // what did not carry over, and why
prusaProjectSettings(text), prusaOverrides(meta)   // a PrusaSlicer .3mf's settings in Orca's form
```

Rust has the same surface in snake case: `apply_easy`, `goal_easy`, `import_orca`, `export_orca`, `read_preset_bundle`, `import_values`, `import_layers`, `build_report`, `validate`, `diff_configs`, `invalidates`, `settings`, `setting_def`, `is_enabled`, `resolve_auto`, `plan_settings`, `apply_plan`.

For callers that do not link the typed API (a CLI, a C ABI, an MCP server, a script) the Rust crate has JSON in, JSON out functions in the shapes the TypeScript package uses: `plan_json`, `apply_plan_json`, `validate_json`, `apply_easy_json`, `resolve_auto_json`, `catalog_json` (the ids a plan request can use), `import_profile_json`, `import_project_json` and `export_profile_json`. `import_project` reads the three text files of a project; unzipping the `.3mf` belongs to sx-core's 3MF reader. Rust and TypeScript run the same cases (`fixtures/plan-cases.json`, `fixtures/import-cases.json`) and must produce the results in `fixtures/plan-golden.json` and `fixtures/import-golden.json`; `UPDATE_GOLDEN=1 pnpm test` rewrites the golden files from the TypeScript side. `SliceStage` is defined in `sx-settings`; `sx-core` can reuse it.

Notes for callers:

- `planSettings` builds a plan in this order: the Orca profile for the target (`opts.target`, or the printer's baseline process), filament `pilot_defaults` and printer facts except for keys in `opts.tuned` (set by a printer specific profile), stored calibration results (`opts.calibrations`), the merged goals (`opts.intent`, from `knowledge/intents` and its pair rules), clamps, then a diff against the current values. Each change carries `origin`, `klass` (`edit`, `guarded` or `read` from the settings catalog) and `approval` (`ask` when a guarded key lands outside the filament's range). Values past a printer limit on a guarded key go to `refused`; every other clamp is recorded in `clamps`. An abrasive material on a soft nozzle puts a message in `blockers` and leaves `changes` empty. `questions`, `caveats`, `advice` and `tellUser` carry what must be asked, shown or said. `applyPlan` skips `read` changes unless `includeRead` is set.
- `planSettings` takes knowledge ids (`filament: 'petg'`, `printer: 'prusa_mk4s'`). With a `base` config, `before` is the base value; without one it is the old setup's knowledge value. Changing the nozzle also rescales layer height and line widths when `base` has them. `warnings` covers a nozzle that is too small or soft, a printer that cannot suit the material, a hotend or bed that is too cool, and drying.
- `importProject` takes the parsed `Metadata/project_settings.config` plus the two optional XML files as text; unzipping is the caller's job. Values Orca keeps outside presets (`filament_colour`, `wipe_tower_x`, `flush_volumes_matrix`) come back raw in `extras`. Keys only Bambu Studio defines stay in `unknownKeys`.
- `readPresetBundle` reads an OrcaSlicer bundle (`.orca_printer`, `.orca_filament`, `.orca_bundle`), a Bambu Studio bundle (`.bbscfg`, `.bbsflmt`) or a plain zip of preset files, given its unzipped entries, and returns each preset with its kind. User presets have no `type`, so the kind comes from the bundle folder or the settings id in the file. It skips paths that climb out of the archive and entries over 2 MB, and refuses more than 500 presets.
- `importPresetFiles` resolves each preset's `inherits` chain against the other files first, since Bambu Studio's own filaments inherit from a user base preset, then against the maker profiles in `packages/profiles` (`vendorParent`). Each preset comes back with its values and a report. The report lists every setting that did not carry over with its label, the old value, the reason (no such setting, a value SlicerX cannot use, or obsolete) and the value used instead, with its source: the preset, the parent profile, the printer profile or the schema default. Where `import-nearest.json` has a close setting or value, the report names it. Settings that mapped cleanly are left out, and settings the old preset never had appear only as a count. `fixtures/preset-files` holds real bundles from OrcaSlicer 2.4.2 and Bambu Studio 2.8.2 (`scripts/make-preset-bundles.py`) and a PrusaSlicer 2.9.6 project (`scripts/make-prusa-project.py`).
- `applyEasy` needs the unmodified merged profile (process, filament and printer parts through `mergeConfigs`). Speed scaling multiplies its values, so applying twice scales twice. A speed cap only limits an increase and never lowers a value below the profile's own.
- Most speed and temperature keys are per-extruder lists in this Orca version (`outer_wall_speed` is `[200, 350]`). Lists stay lists.
- A key with any `nil` entry is left out of the config and listed in `nilKeys`.
- `min` and `max` are the Pilot bounds from `knowledge/settings.yaml` where the catalog has the key. Orca's own limits are `orcaMin` and `orcaMax` when they differ; `validate` errors only outside Orca's limits and warns outside the recommended range.
- Conflict checks judge only keys the config sets, so a partial config is not held to defaults it never chose.

## Regenerating

```sh
node scripts/gen-profiles.mjs             # after the printer catalog or scripts/printer-specs.json changes
python3 scripts/gen-easy-cases.py
pnpm gen:knowledge                      # after knowledge/ changes
pnpm gen:reference                      # after schema.json changes
```

`schema.json` and `legacy.json` are checked in as this package's own data: facts (keys, types, units, defaults, ranges, key renames) and labels written for SlicerX in `scripts/labels.json`. Edit them directly; `fixtures/knowledge-catalog.json` is the bounds table the tests compare with the schema.
