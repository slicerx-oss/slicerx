# supabase

Database schema, row level security, seed data and policy tests for SlicerX. Everything here runs on a local Supabase stack. App code only ever holds the project URL and the anon key, and the service role key stays out of `apps/` and out of git.

The library is free and moderated. There is no pricing in the schema: no subscriptions, tiers, licenses or payouts.

## Modules

The schema is split into module migrations so the store and cloud can be removed without touching sign-in:

| Migration | Module | Contents |
| --- | --- | --- |
| `migrations/0001_auth.sql` | auth | `profiles` with a role (`owner`, `moderator`, `creator`, `member`) and ban fields; role helpers; the append-only `audit_log`; `set_user_role`, `ban_user`, `unban_user`; `api_tokens` with per-token rate limits; `paired_devices` for the phone; account export (`export_my_data`) and deletion with a 30 day grace period |
| `migrations/0002_store.sql` | store | `library_settings`, creator pages (`creators`, `creator_links`, `creator_featured`), follows, listings, immutable listing versions with scan and review status, verified file manifests, print profiles, likes, comments, makes, collections, downloads, `storage_cleanup`, the review queue view and moderation functions, the upload scan functions, and the `uploads-quarantine` and `listing-files` buckets |
| `migrations/0005_anon_downloads.sql` | store | Downloads without signing in: per-IP limits in `library_settings`, the IP hash salt, hourly usage per IP hash, daily anonymous counts per listing, short-lived `download_grants`, `request_download`, `set_anon_downloads` and the anon storage policy on `listing-files` |
| `migrations/0013_creator_pages.sql` | store | Creator page banners (`creators.banner_url`), the public `creator-media` bucket for banners and logos (writes only under the member's own id), the private Saved list (`collections.kind = 'saved'`, `set_saved`, `saved_listings`), and the library rows: `trending_listings`, `new_creators` and `recommended_listings` |
| `migrations/0004_cloud.sql` | cloud | devices, synced profiles, printers and fleets, the `cloud_jobs` queue, deliveries, and the private `cloud-inputs` and `cloud-results` buckets |
| `migrations/0012_bug_reports.sql` | bug reports | `bug_reports`, written only through `submit_bug_report` (10 an hour per install, 200 an hour overall), read by the Discord poller with the service key, and the private `bug-reports` bucket (docs/bug-intake.md) |

The store depends on auth, and cloud only on auth. `modules/` has a drop script per module and a check that auth still works after both run (see `modules/README.md`). Roles, bans, the audit log and paired devices live in auth, so they survive dropping the store. The seed is `seed/auth.sql` and `seed/store.sql`, generated by `pnpm --filter @slicerx/store seed:write`. Do not edit it by hand.

## Roles

| Role | Can |
| --- | --- |
| owner | Everything a moderator can, plus assign roles, change the moderation mode, mark creators trusted. One per deployment, set with the service role. |
| moderator | See the review queue and audit log, approve and reject uploads (unless the mode is `owner-approves-all`), remove listings, delete comments, ban accounts (not the owner or other moderators). Cannot review their own uploads. |
| creator | Everything a member can, plus manage their own creator page, links, featured models and listings. Made automatically when a member creates a creator page. |
| member | Browse, like, comment, collect, download, add makes, follow, manage their own tokens and devices. |
| banned | A member with `banned_at` set. Cannot write anything. Their listings and page are hidden, their tokens and sessions are revoked, and sign-in is blocked. |

Clients never write `profiles.role` or the ban columns; the functions above do, and each writes an `audit_log` row.

## Moderation

Listings start `pending` and are visible only to their creator and staff. Staff approve or reject through functions, never by updating rows:

- `approve_listing(listing, note)` approves the listing and every version waiting on it. Every waiting version must have passed the scan.
- `reject_listing(listing, reason)` needs a reason of 3 or more characters, shown to the creator. On an approved listing it rejects only the waiting versions.
- `remove_listing(listing, reason)` takes a public listing down.
- `ban_user(user, reason)` and `unban_user(user)`.
- The `moderation_queue` view lists pending listings and approved listings with a new version waiting, only for staff.

Creators can archive and restore their own listings and resubmit a rejected one. Editing the title, description, license, tags or cover of an approved listing sends it back to review. A new version on an approved listing goes to the queue while the old version stays public.

The moderation mode lives in `library_settings` and comes from the edition config (`library.moderation`). `apply_library_settings(mode, max_file_mb, formats)` copies it in and sets the bucket size limits, and the owner can change the mode with `set_moderation_mode`:

| Mode | Who approves |
| --- | --- |
| `owner-approves-all` | Only the owner (default). |
| `moderators` | Owner and moderators. |
| `trusted-creators` | Owner and moderators; a clean upload from a creator the owner marked trusted is approved at once. |
| `auto-after-scan` | Every clean upload is approved at once; staff review afterwards and can remove it. |

## Uploads

Files reach storage only through the scan pipeline:

1. The client inserts a listing (`pending`) and a `listing_versions` row (`scan_status = 'uploading'`) whose `storage_path` is `<listing id>/<version id>/<file name>` with a `3mf`, `sx3mf` or `stl` extension.
2. The client uploads the file to the private `uploads-quarantine` bucket at that path. Storage policy: only for a version row in `uploading` state, for a listing the caller edits, and not banned.
3. The client calls `submit_version(version)`, which queues it.
4. The scan service (service role) calls `claim_scan(worker)`, checks the file, copies it to `listing-files`, calls `finish_scan(version, ok, report, sha256, size, parts)` and deletes the quarantine object. If the scanner itself fails it calls `retry_scan(version, error)`, which requeues up to three times. `requeue_stale_scans(older_than)` recovers dead workers.
5. Staff approve the listing. Anyone can then download it (see "Downloads").

Clients cannot set scan or review status, write to `listing-files`, or write the file manifest. Deleting a listing or an account queues its storage prefixes in `storage_cleanup` for the service to remove.

## Downloads

`request_download(listing)` starts every download and returns the newest approved, clean version of a public listing. It never returns a pending, rejected, archived or removed listing, or a version still waiting for review.

- Signed-in members are counted in `downloads` with no limit. They read the file with a signed URL from `listing-files`, which `can_download` gates.
- Visitors are counted per IP and get a grant: a random `sxg_` token for that one file, valid for `grant_seconds` (120 by default). They read the file with `GET /storage/v1/object/authenticated/listing-files/<path>`, the anon key and the header `x-sx-download-grant: <token>`. The storage policy accepts the grant only on that direct read (`storage.operation` is `get_authenticated` or `info_authenticated`). Signing is refused, so a grant cannot become a long-lived URL. The file's approval is checked again on every read, so a takedown also closes grants already issued. Preview images of public versions need no grant.
- The limit is `anon_per_hour` (20) and `anon_per_day` (60) per IP. Over it, the call fails with hint `rate_limited` and the client returns the `rate_limited` code. The owner changes the limits, or turns visitor downloads off, with `set_anon_downloads(enabled, per_hour, per_day)`, which is audited.
- IPs are never stored. Usage rows hold an HMAC of the IP and the date under a private salt, so they cannot be linked across days, and rows older than two days are pruned as downloads come in.
- `library_settings.client_ip_source` names the header that holds the client IP. The default, `x-forwarded-for-last`, is the hop the local Kong gateway appends. Behind Cloudflare use `cf-connecting-ip`. A header the client can set (Kong passes a client-sent `cf-connecting-ip` through unchanged) lets a visitor pick their own bucket.
- `listing_stats` and `creator_dashboard` add anonymous downloads to the member count.

## Access rules

Anyone can read approved listings with their versions, files, print profiles, comments, makes and likes, and creator pages with their links. Comments and collections are deferred past v1: the schema keeps them, and the SlicerX edition's store client leaves them off (packages/store README). Pending, rejected, archived and removed listings are visible to their creator and staff. The audit log and queue are staff only. Members read their own follows, downloads, API tokens, paired devices and deletion requests. Grants, IP usage, anonymous counts and the salt have no client access.

API tokens are stored as SHA-256 hashes, and the plain token is returned once by `create_api_token`. Clients cannot read the hash column. Only the service role can call `resolve_api_token`, for the cloud endpoint behind the MCP server and the CLI. It maps a token to its user and scopes and counts the request against the token's per-minute limit.

Creator links accept https URLs only. A link to a named service (Patreon, MakerWorld, Printables, Thingiverse, Cults3D, YouTube, Instagram, TikTok, X, Discord, GitHub, Ko-fi, Buy Me a Coffee) must be on that service's domain. A page has at most 12 links.

Members can export their data with `export_my_data()` and schedule deletion with `request_account_deletion()`, which revokes their tokens at once. `purge_due_accounts()` runs on the service role once the 30 days are up. It anonymizes the member's comments and deletes the auth user, which cascades to their creator page and uploads. The owner account cannot be deleted. `account_deletion_policy()` lists what is removed and what is kept.

## Run it

The images take several GB, so check free disk first.

```
supabase start -x studio,imgproxy,logflare,vector,edge-runtime,supavisor
supabase db reset
supabase test db
modules/check-drop.sh
```

A hosted project created with "automatically expose new tables" off gives `anon` and `authenticated` no table privileges, while the local stack gives them everything. `migrations/0009_api_role_grants.sql` grants each role exactly the commands its row level security policies allow, so both end the same, and `tests/grants.test.sql` checks that match. `tests/no-default-grants.sh` runs the whole suite on a second stack without default privileges (project `slicerx-nogrants`, ports 55320 to 55329).

Realtime stays on: paired devices report a revoked phone through it. Magic link emails go to the local mail catcher at http://127.0.0.1:54324. The auth blocks in `config.toml` (site URL, allowed redirects, OAuth providers) are generated from the edition config by `pnpm --filter @slicerx/store supabase:config`.

## Hosted library

`pnpm --filter @slicerx/store library:settings` applies the edition's `library.moderation` values. `pnpm --filter @slicerx/store library:seed --models <folder>` seeds the starter library from model files kept outside git (see `packages/store/scripts/seed-library.ts`). Both read the service role key from the environment.

## Status

- `supabase db reset` applies the four migrations and the seed with no errors.
- `supabase test db` passes 468 tests across `rls`, `roles`, `moderation`, `creator`, `upload`, `account`, `anon_download` and `cloud`.
- `modules/check-drop.sh` drops the cloud and store modules in a rolled-back transaction and confirms that profiles, roles, API tokens, the sign-up trigger, export and deletion still work.
- The seed has 20 fictional users (an owner, a moderator, 5 creators, 12 members and one banned member), 5 creator pages with links and featured models, and 26 listings in every state.
